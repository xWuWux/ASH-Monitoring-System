# k6 API load test

Runs authenticated load against the Docker Compose API after
`tests/performance/k6/seed.sql` has inserted 500,000 command rows over
30 days, 20,000 sessions, and 50,000 file changes. The last 24 hours contain
roughly 16.7k command rows, which keeps the time-window queries selective.

## What it covers

| Endpoint | Query |
|---|---|
| `events` | `GET /api/v1/events?limit=50` |
| `hosts` | `GET /api/v1/hosts` |
| `stats_timeline` | `GET /api/v1/stats/timeline?hours=24` |
| `stats_top_commands` | `GET /api/v1/stats/top-commands?hours=24&limit=20` |
| `sessions` | `GET /api/v1/sessions?limit=50` |

Each endpoint has its own threshold:

- **Always enforced:** failed requests `< 1%`, checks (status 200 + JSON
  content type) `> 99%`. A 503/timeout/non-JSON response fails the run even
  during latency calibration.
- **Latency targets, report-only during calibration:** average `< 200 ms`,
  p95 `< 500 ms`. The first 2–3 main runs set `K6_ENFORCE=false`; once a
  baseline proves the latency targets are achievable on the runner, set
  `K6_ENFORCE=true` in `ci.yml`.

## Local run

```bash
# From the repository root, with the Compose stack already running. The
# seed truncates audit tables, so it requires an explicit confirmation.
ASH_SEED_CONFIRM=disposable \
  docker compose -f deployments/docker/docker-compose.yml exec -T \
    -e PGPASSWORD="$ASH_DB_PASSWORD" postgres \
    psql -U ash -d ash_logs -v ON_ERROR_STOP=1 \
    < tests/performance/k6/seed.sql

mkdir -p k6-results

k6 run \
  -e ASH_API_BASE_URL=http://127.0.0.1:8080 \
  -e ASH_ADMIN_USER="${ASH_ADMIN_USER:?set ASH_ADMIN_USER}" \
  -e ASH_ADMIN_PASS="${ASH_ADMIN_PASS:?set ASH_ADMIN_PASS}" \
  -e K6_VUS=20 \
  -e K6_DURATION=60s \
  -e K6_ENFORCE=false \
  --summary-export=k6-results/summary.json \
  tests/performance/k6/api-load.js
```

`ASH_ADMIN_USER`/`ASH_ADMIN_PASS` are the credentials generated by
`scripts/install.sh` or the CI environment, not the old `admin`/`admin`
defaults.

## Notes

- The API has four synchronous gunicorn workers and one PostgreSQL in this
  Compose stack. 20 VUs is a CI-sized load, not a capacity benchmark for
  thousands of users; a pre-production environment with a reverse proxy is
  required for that.
- The stack has no ingress, so 502/504 cannot be produced. The failure gate
  covers 5xx/503, timeouts, and non-JSON responses.
- `tests/performance/load_api.py` remains the small every-PR regression
  guard. This k6 test runs in the main/manual ephemeral job because it needs
  the seeded stack and ~2 minutes.
